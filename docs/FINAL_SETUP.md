# TABLE — финальная настройка и сдача

## 1. Подготовка

Создайте виртуальное окружение: `python3 -m venv .venv && source .venv/bin/activate`.
Установите зависимости: `python -m pip install -r requirements.txt -r requirements-dev.txt`.
Задайте `SECRET_KEY` (длинная случайная строка), `ADMIN_USERNAME`, `ADMIN_PASSWORD`.
Для локального HTTP оставьте `COOKIE_SECURE=0`, для HTTPS в публикации `COOKIE_SECURE=1`.
Не публикуйте `restaurant.db`, пароли, `.env` и логи. Перед любыми испытаниями сохраните резервную копию.

## 2. Настоящая отправка email

Укажите в окружении `SMTP_HOST`, `SMTP_PORT` (обычно 587 для STARTTLS или 465 для SSL), `SMTP_SSL` (0/1), `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`.
У разных почтовых сервисов нужны специальные пароли приложений или SMTP-токены. Не записывайте их в исходный код.
Проверка подключения БЕЗ отправки: `python scripts/check_smtp.py`.
Отправить одно тестовое письмо на свой адрес: `python scripts/check_smtp.py --send-to YOUR_EMAIL`.
Доставка зависит от провайдера, спам-фильтров и DNS; её нужно подтвердить по факту получения.

## 3. Напоминания каждые 15 минут

Команда `python maintenance.py reminders` отправляет письма для подтверждённых броней в ближайшие 24 часа, не отправленные ранее.
На macOS/Linux: `bash scripts/install_reminder_cron.sh`, затем перенесите предложенную строку в `crontab -e`.
**Важно:** cron должен получать SMTP-переменные окружения; простой запуск в Terminal не передаёт их автоматически в cron.
На Mac при необходимости используйте launchd вместо cron. Запускайте команду один раз вручную и проверяйте журнал.

## 4. Тесты и GitHub Actions

Локально: `bash scripts/run_checks.sh` (требуется Node.js).
Тесты используют временную БД и не должны менять настоящую `restaurant.db`.
Файл `.github/workflows/quality.yml` автоматически запускает проверки при push и pull request в GitHub.
После загрузки репозитория откройте вкладку Actions и убедитесь, что все задания зелёные.
Не копируйте настоящий `restaurant.db` в публичный репозиторий.

## 5. Нагрузочное тестирование

В одном терминале запустите Flask: `python app.py`. Во втором: `bash scripts/run_load_test.sh`.
По умолчанию: 5 пользователей, 1 новый пользователь/сек, 30 секунд. Тест только на localhost, запросы только на чтение.
Отчёты появятся в `reports/locust.html` и `reports/locust_stats.csv`.
Запишите реальный p95, RPS и ошибки из Locust; не выдавайте пустые шаблоны за результаты.

## 6. Проверка трёх языков и интерфейса

`python scripts/audit_locales.py --strict` проверяет наличие казахского и английского переводов в словаре.
В браузере вручную проверьте RU/KK/EN для главной страницы, регистрации, входа, личного кабинета, админ-панели, оплаты, ошибок и динамических сообщений. Словарная проверка не доказывает полноту перевода UI.
Проверьте темы, клавиатуру (Tab/Enter/Escape), экран телефона и Safari/Chrome.

## 7. Финальные пользовательские сценарии

1. Зарегистрировать нового пользователя, выйти, войти.
2. Создать бронь и предзаказ, увидеть в личном кабинете и админке.
3. Повторить бронь того же столика на пересекающееся время: должен быть конфликт.
4. Отменить бронь, проверить её статус и уведомление.
5. Проверить невозможность доступа обычного пользователя к API администратора.
6. Создать резервную копию: `python maintenance.py backup`.
7. Проверить `/health`, логи и отчёт о тестах.
8. Провести демонстрацию по `docs/DEMO_SCRIPT.md`.

## Ограничения

Реальная отправка писем требует реквизитов SMTP и доступа к почтовому серверу. Нагрузочный тест и браузерная проверка требуют запущенного приложения. CI станет активным только после публикации файлов в GitHub. Эти действия не считаются выполненными до проверки пользователем.
