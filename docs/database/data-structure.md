# Структура данных системы

## Проект

Система бронирования столиков ресторана

## 1. Общая структура

Для хранения данных система использует реляционную базу данных SQLite.

Основными сущностями системы являются:

1. Пользователь (`users`)
2. Бронирование (`reservations`)

Пользователь может иметь несколько бронирований.
Каждое бронирование может быть связано с зарегистрированным пользователем.

---

# 2. Сущность User

Таблица: `users`

Используется для хранения зарегистрированных пользователей системы.

| Поле | Тип | Назначение |
|---|---|---|
| id | INTEGER | Уникальный идентификатор пользователя |
| name | TEXT | Имя пользователя |
| phone | TEXT | Номер телефона |
| email | TEXT | Email пользователя |
| password_hash | TEXT | Хеш пароля |
| created_at | TEXT | Дата и время регистрации |

## Ограничения

- `id` является первичным ключом.
- `email` должен быть уникальным.
- имя обязательно;
- телефон обязателен;
- email обязателен;
- пароль хранится только в виде хеша.

---

# 3. Сущность Reservation

Таблица: `reservations`

Используется для хранения бронирований столиков.

| Поле | Тип | Назначение |
|---|---|---|
| id | INTEGER | Уникальный номер бронирования |
| table_number | INTEGER | Номер столика |
| customer_name | TEXT | Имя посетителя |
| phone | TEXT | Телефон посетителя |
| guests | INTEGER | Количество гостей |
| reservation_date | TEXT | Дата бронирования |
| reservation_time | TEXT | Время бронирования |
| status | TEXT | Статус бронирования |
| user_id | INTEGER | Идентификатор зарегистрированного пользователя |
| payment_status | TEXT | Статус оплаты |
| payment_method | TEXT | Способ оплаты |
| paid_at | TEXT | Дата и время оплаты |

---

# 4. Статусы бронирования

Система использует следующие значения:

- `confirmed` — бронирование подтверждено;
- `arrived` — посетитель прибыл;
- `completed` — посещение завершено;
- `cancelled` — бронирование отменено.

Активными считаются:

- `confirmed`;
- `arrived`.

Только активные бронирования блокируют столик.

---

# 5. Данные оплаты

Для бронирования сохраняются:

- `payment_status`;
- `payment_method`;
- `paid_at`.

Основные состояния оплаты:

- `unpaid` — не оплачено;
- `paid` — оплачено;
- `refunded` — оформлен возврат после отмены.

Поддерживаемые DEMO-способы оплаты:

- `card`;
- `kaspi`;
- `apple_pay`.

---

# 6. Связь пользователя и бронирования

Поле:

`reservations.user_id`

используется для связи бронирования с зарегистрированным пользователем.

Связь:

`users.id → reservations.user_id`

Тип связи:

`1:N`

Один пользователь может иметь несколько бронирований.

Одно бронирование может принадлежать одному зарегистрированному пользователю.

Поле `user_id` может быть пустым, поскольку система также позволяет создавать бронирования без зарегистрированного аккаунта.

---

# 7. Данные столиков

В текущей версии проекта столики задаются в конфигурации приложения.

Используются следующие столики:

| Столик | Вместимость |
|---:|---:|
| 1 | 2 |
| 2 | 4 |
| 3 | 4 |
| 4 | 6 |
| 5 | 2 |
| 6 | 4 |
| 7 | 4 |
| 8 | 6 |

Отдельная таблица `tables` в текущей реализации не используется.

Номер столика сохраняется в поле `table_number` бронирования.

---

# 8. Итог

Разработанная структура данных позволяет хранить информацию о пользователях, бронированиях, статусах и DEMO-оплате.

Структура соответствует функциональным требованиям системы бронирования столиков ресторана.
