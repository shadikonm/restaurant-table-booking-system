# ADR-001: Выбор модели поставки проекта

**Статус:** Принято  
**Дата:** 15.09.2026  
**Проект:** Система бронирования столиков в ресторане

## 1. Контекст

Разрабатывается информационная система бронирования столиков в ресторане.

Система должна позволять пользователям просматривать доступные столики, выбирать дату и время, создавать и отменять бронирования. Администратор ресторана должен иметь возможность просматривать и управлять бронированиями.

Проект является учебным IT-проектом и выполняется небольшой командой в условиях ограниченного времени. На начальном этапе все требования к системе могут быть определены не полностью и могут уточняться в процессе разработки.

Поэтому необходимо выбрать модель поставки, которая позволит получить работающий результат за короткий срок, регулярно проверять результаты разработки и при необходимости изменять требования.

## 2. Драйверы решения

При выборе модели поставки учитываются следующие факторы:

1. Ограниченные сроки разработки.
2. Небольшой размер команды.
3. Необходимость создания работающего MVP.
4. Возможность изменения и уточнения требований.
5. Необходимость регулярно тестировать результат.
6. Возможность распределять задачи между участниками команды.
7. Простота контроля прогресса проекта.
8. Возможность поэтапно добавлять функциональность.

## 3. Рассмотренные варианты

### Вариант 1 — Agile с итеративной разработкой MVP

Проект разрабатывается небольшими итерациями. Сначала создаётся минимально работоспособная версия системы, после чего функциональность постепенно расширяется.

В MVP входят основные функции:

- просмотр доступных столиков;
- выбор даты и времени;
- создание бронирования;
- отмена бронирования;
- просмотр бронирований администратором.

На следующих итерациях могут добавляться дополнительные функции.

**Плюсы:**

- позволяет быстро получить работающий продукт;
- подходит для небольшой команды;
- позволяет изменять требования;
- облегчает регулярное тестирование;
- позволяет получать промежуточные результаты;
- удобно управлять задачами через Kanban-доску.

**Минусы:**

- требуется регулярно контролировать задачи;
- первоначальный план может изменяться;
- необходимо постоянно определять приоритеты;
- часть второстепенных функций может не попасть в MVP.

**Решение:** выбран.

### Вариант 2 — Waterfall

Разработка выполняется последовательно по этапам:

1. сбор требований;
2. анализ;
3. проектирование;
4. разработка;
5. тестирование;
6. внедрение.

**Плюсы:**

- чёткая последовательность этапов;
- требования и документация определяются заранее;
- проще планировать проект на начальном этапе;
- удобно для проектов с устойчивыми требованиями.

**Минусы:**

- изменения требований после начала разработки вносятся сложнее;
- рабочий продукт появляется поздно;
- ошибки предыдущих этапов могут обнаружиться только на поздних этапах;
- менее гибкая модель для учебного проекта.

**Решение:** отвергнут.

Waterfall не выбран, поскольку требования к системе могут уточняться во время разработки, а команде необходимо регулярно получать работающие результаты.

### Вариант 3 — Big Bang

Разработка начинается с минимального планирования. Команда сразу приступает к реализации системы, а основные решения принимаются непосредственно в процессе разработки.

**Плюсы:**

- можно быстро начать разработку;
- минимальные затраты времени на предварительное планирование;
- подходит для небольших экспериментальных задач.

**Минусы:**

- высокий риск потери контроля над проектом;
- сложно прогнозировать сроки;
- сложно отслеживать прогресс;
- повышается риск несогласованности компонентов;
- тестирование может быть отложено;
- конечный результат сложнее прогнозировать.

**Решение:** отвергнут.

Big Bang не выбран, поскольку проект требует понятного распределения задач, контроля прогресса и регулярного получения промежуточных результатов.

## 4. Решение

Для проекта выбрана итеративная Agile-модель разработки с использованием подхода MVP.

Разработка будет выполняться небольшими итерациями.

На первой итерации планируется создать базовую версию системы, включающую просмотр доступных столиков, выбор даты и времени и создание бронирования.

На следующих итерациях будут реализованы отмена бронирований, управление бронированиями администратором, улучшение интерфейса и дополнительные функции.

Предварительное распределение итераций:

**Итерация 1:** анализ требований и проектирование системы.

**Итерация 2:** разработка основного механизма бронирования.

**Итерация 3:** разработка пользовательского интерфейса и административной части.

**Итерация 4:** тестирование и исправление ошибок.

**Итерация 5:** финальная доработка и подготовка документации.

## 5. Последствия решения

### Положительные последствия

- Команда быстро получает работающий MVP.
- Функциональность можно добавлять постепенно.
- Изменения требований проще внедрять.
- Ошибки выявляются раньше.
- Прогресс проекта легко отслеживать через GitHub Projects.
- Команда регулярно получает промежуточные результаты.
- Приоритет можно отдавать наиболее важным функциям системы.

### Отрицательные последствия и потери

Выбирая Agile и MVP, команда теряет часть предсказуемости первоначального плана.

В частности:

- не все функции будут реализованы с самого начала;
- объём проекта может измениться;
- часть дополнительных функций может не попасть в итоговую версию;
- необходимо регулярно обновлять задачи и приоритеты;
- требуется постоянная коммуникация между участниками команды;
- итоговый набор функций может отличаться от первоначального плана.

Несмотря на это, для учебного проекта преимущества итеративной разработки превышают её недостатки.

## 6. Итог

Для системы бронирования столиков выбрана итеративная Agile-модель разработки с использованием MVP, поскольку она соответствует ограниченным срокам проекта, небольшому размеру команды и возможности уточнения требований в процессе разработки.
